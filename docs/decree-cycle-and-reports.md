# 旨意周期与回报机制重排

本文专门处理两个最容易破坏体验的问题：

1. 玩家已经下旨，为什么界面却像“下达”还要十几天。
2. 任务做完后的“回报”到底是御案复命，还是奏对追问，还是履约回访。

结论：当前系统不是完全没有规则，而是把 **下达、传旨、执行、复命、追问** 混成了同一条进度，导致近身处置、内廷身份转换和地方大政使用了同一个时间模型。重构后必须把这些阶段拆开。

---

## 现状诊断

### 1. 通用旨意生命周期过宽

当前 `ming_sim/lifecycle.py` 的核心生命周期是：

```text
issued -> in_transit(送达) -> executing(承办) -> done(复命)
```

`build_chain()` 会按 `content/directive_categories.json` 归类后计算：

- `lead_days = max(1, round(category.lead_days * distance))`
- `exec_days = max(2, round(category.base_days * ability_factor * distance * resistance_factor * ...))`
- `eta_day = start_day + lead_days + exec_days`

这套模型适合“赈济陕西”“整饬辽饷”“修筑边墙”这类要经过驿传、部议、地方承办的事项；但它不适合“殿内下令净身某人”“当场革去某人差遣”“内廷即刻收押”这类近身处置。

根因是：

- `lead_days` 在配置里是“诏书送达天数”，但 UI 和玩家体感会把它理解成“下达耗时”。
- `lead_days` 最少 1 天，`exec_days` 最少 2 天，导致没有真正的同日办结路径。
- 分类器只看旨意文本和地区，缺少“目标是否在京/在殿/在内廷”“是否属于即时身体或身份处置”的判断。
- 一些动作本来已有即时 API，却没有被普通旨意入口统一复用。

### 2. 净身已经有即时路径，但普通旨意会绕开

当前代码里已经存在即时净身路径：

- `web_app.py::castrate_official()` 会直接执行身份转换。
- `/api/recruitment/castrate` 会调用该方法。
- `AudienceView` 对应的待确认动作里，`_execute_castration_action()` 会当场返回“已改入内廷”。
- `dialogue_goals.py` 把 `castration` 列入 `INSTANT_AGREEMENT_ACTIONS`。

所以问题不是“系统不能当天净身”，而是：当玩家用普通诏旨表达“下旨净身某人”时，它被送入通用 `lead_days + exec_days` 模型，变成了像地方工程一样等待送达和承办。

### 3. 回报口径混乱

当前至少有三类“回报”：

| 名称 | 数据来源 | 玩家入口 | 本质 |
|------|----------|----------|------|
| 御案复命 | `edict_outcome.py` 写入 `memorials(kind='复命')` | 御案 | 正式结果通知，来自一道已办结旨意 |
| 诏旨复盘/追问 | `EdictsView` 召主办，`directive_followup` | 诏旨/召对 | 对已复命或在办旨意的口头追问 |
| 奏对履约回访 | `conversation_goals` / `negotiation_agreements` / `monthly_followups` | 召对 | 对承诺、旧约、条件的履约核查 |

这三者都可能在文案里被叫成“回报”，玩家自然会混淆。后续必须统一命名：

- **复命**：只给御案正式结果通知使用。
- **追问/复盘**：只给诏旨完成后的召对使用。
- **履约回访**：只给奏对承诺和协议账本使用。
- **密揭/密奏**：只给密查、密令结果使用。

## 正确语义模型

每道旨意必须拆成五个阶段：

| 阶段 | 是否耗时 | 说明 | UI 名称 |
|------|----------|------|---------|
| 成命 | 不耗时 | 玩家确认颁行后，旨意立即成立并入档 | 已下达 |
| 传旨 | 可为 0 | 是否需要把命令送到远方、部院、军镇或地方 | 传旨中 / 已传达 |
| 承办 | 可为 0 | 实际办理、部议、调拨、执行、地方落地 | 承办中 |
| 复命 | 通常同完成日 | 正式结果回到御案，形成 `复命` 奏报 | 已复命 |
| 复盘 | 可选 | 皇帝召主办追问水分、责任、下一手 | 追问复盘 |

关键原则：

1. **下达永远不应显示为十几天。** 旨意确认即为已下达。
2. 耗时只能来自 **传旨** 和 **承办**。
3. 内廷、殿内、京师近身处置可以 `delivery_days=0`、`work_days=0/1`。
4. 地方、军镇、工建、税制改革才使用距离和长工期。
5. 完成后的正式结果统一叫 **复命**，落御案；追问复命不等于再次结案。

## 新时间类型

### A. 同日直接处置

适用：

- 强旨净身、奴籍/内廷身份转换。
- 当场收押、廷杖、逐出御前。
- 殿内或内廷直接任差、撤差。
- 近侍旧患调养、宝匣封存等内廷档案动作。

时间规则：

| 字段 | 值 |
|------|---|
| `delivery_days` | 0 |
| `work_days` | 0 或 1 |
| `expected_report_day` | 当日或次日 |

落库规则：

- 仍可创建 `turn_directives` 记录，作为皇命证据。
- 但 `lifecycle_status` 可直接为 `done`，或新增 `resolved_same_day`。
- 同日写入 `memorials(kind='复命')` 或更细的 `kind='内廷复命'`。
- 对人物身份、关系、怨气、政治反应的变更必须当场落库。

玩家体验：

```text
已下达：强旨净身张三。
已办结：张三已改入内廷，旧档封存。
可追问：召主办复盘后患、怨望与差遣风险。
```

### B. 京师/部院短程命令

适用：

- 任免京官。
- 命部院查账、覆议、具奏。
- 命锦衣卫/东厂先行探查京中线索。

时间规则：

| 字段 | 值 |
|------|---|
| `delivery_days` | 0-1 |
| `work_days` | 1-7 |

这类旨意不应该因为默认地区是北直隶就被套成地方行政流程。若主办、目标、执行机构都在京，应显示“已下达，部院承办中”，而不是“送达中”。

### C. 文书转行与普通行政

适用：

- 发部议。
- 要求地方巡抚查奏。
- 常规钱粮调拨。
- 常规人事铨选。

时间规则：

| 字段 | 值 |
|------|---|
| `delivery_days` | 1-5，受距离影响 |
| `work_days` | 3-20，受官员能力、阻力、资源影响 |

### D. 地方工程、军务与制度改革

适用：

- 赈济远省。
- 军事行动。
- 建筑修缮。
- 税制、盐法、辽饷大调整。

时间规则：

| 字段 | 值 |
|------|---|
| `delivery_days` | 2-10，受距离影响 |
| `work_days` | 20-90+，受阻力和资源影响 |

这类长周期是合理的，但 UI 必须写清楚：

```text
旨意已下达。
传旨 4 日，预计第 5 日送达陕西。
承办预计 28 日，复命约第 33 日。
```

而不是：

```text
下达还需 33 日。
```

## 旨意调度改造点

### 1. 增加 timing profile

在 `content/directive_categories.json` 或新文件中为类别增加：

```json
{
  "timing_profile": "same_day | capital_short | administrative | field_operation | policy_program",
  "allow_zero_delivery": true,
  "allow_zero_work": true
}
```

类别只是第一层判断。最终 timing 还要看：

- 是否点名具体人物。
- 目标是否在京、在殿、在内廷。
- 是否涉及身体处置、身份转换、直接收押。
- 是否涉及远方地区或军镇。
- 是否需要财政拨款、部议、多人协同。

### 2. 先识别即时动作，再进入通用生命周期

普通旨意入口应先走 `detect_immediate_directive_action(text)`：

| 文本命中 | 应调用 |
|----------|--------|
| 净身、宫刑、发净军、没入内廷 | `castrate_official(force=True)` |
| 赦出内廷、转民籍 | `emancipate_eunuch(force=True)` |
| 当场收押、革差、廷杖 | 人物状态即时处置函数 |
| 殿内任差、撤差 | 人事即时处置函数 |

命中后：

- 创建皇命记录。
- 直接应用状态变化。
- 同日生成正式复命。
- 不再走 `lead_days >= 1`、`exec_days >= 2` 的通用流程。

### 3. 重命名展示字段

数据库字段可以暂时保留 `lead_days` / `exec_days`，但所有玩家文案要改为：

| 旧字段 | 玩家文案 |
|--------|----------|
| `lead_days` | 传旨/送达日数 |
| `exec_days` | 承办日数 |
| `eta_day` | 预计复命日 |

严禁把 `lead_days + exec_days` 叫作“下达周期”。

### 4. 增加“已下达”显式状态

当前 UI 直接把 live status 显示成 `送达中 / 承办中 / 已复命`。应增加一个稳定事实：

```text
成命：第 N 日已下达
传旨：0/3 日
承办：4/20 日
复命：预计第 M 日
```

即使状态是 `in_transit`，也要显示“已下达，传旨中”，避免玩家误读为“还没下达”。

## 回报机制命名边界

### 御案复命

正式来源：

- 一道 `turn_directives` 办结。
- `edict_outcome.py` 生成复命文本和 delta。
- `memorials(kind='复命')` 入御案。

规则：

- 是正式案卷结果。
- `ack` 已阅即可归档，免注意力、无批红后果。
- 可以触发后续追问，但自身就是本次执行的结案结果。
- 玩家应在御案看到“原旨 -> 奉旨复命 -> 结果摘要”。

### 诏旨复盘/追问

来源：

- 玩家在诏旨页对主办官发起追问。
- 对话上下文来自 `directive_chat_context_brief()`。
- 结果写入 followup history 或形成新的旨意/承诺。

规则：

- 它不是正式复命本身。
- 它是对复命真实性、责任归属、下一步方案的审问。
- UI 应叫“复盘”“追问水分”“续下一手”，不要叫“回报”。

### 奏对履约回访

来源：

- `conversation_goals`
- `negotiation_agreements`
- `negotiation_tasks`
- `monthly_followups`

规则：

- 它追的是人和承诺，不是某道旨意的结案。
- 可以产出证词、把柄、草案、承诺、密令。
- 只有当它转成御案、诏旨、账簿或国策证据后，才算正式落地。
- UI 应叫“履约回访”“旧约追问”“条件待证”，不要与复命混名。

### 密查/密令回报

来源：

- `secret_orders`
- `veil`
- 密揭、密奏、暗线核议。

规则：

- 若证据可公开裁断，进入御案为“密揭到案”。
- 若仍需问承办人，进入召对为“密令追问”。
- 不能静默混入普通奏对回访。

## UI 调整清单

### 诏旨页

每道旨意展示为：

```text
已下达：第 12 日
阶段：传旨中 / 承办中 / 停摆 / 已复命 / 已收回
传旨：0/3 日
承办：6/20 日
预计复命：第 35 日
```

同日直接处置展示为：

```text
已下达并办结
复命已入御案
可召主办复盘
```

### 御案页

继续保留复命置顶，但文案要强调：

```text
复命是正式结果通知，不消耗注意力；已阅仅归档。
```

### 召对页

把“回报”分成：

- `差使复命`：只用于某个 NPC 主动就旧差来说明情况。
- `履约回访`：旧约、条件、承诺账本。
- `复命追问`：来自某道已复命旨意。

### 首页

只显示摘要：

```text
今日复命 2 道；其中 1 道建议追问水分。
履约逾期 1 件；非正式复命，需召对核证。
```

## 与国策中枢的关系

国策中枢只收证据，不抢执行。

| 来源 | 进入国策的方式 |
|------|----------------|
| 御案复命 | 作为已执行证据 |
| 复命追问 | 作为执行质量证据 |
| 奏对履约回访 | 作为人物/派系站队证据 |
| 密揭/密令 | 作为风险或把柄证据 |
| 同日直接处置 | 作为高风险国策工具证据 |

例如“强旨净身某文官”：

1. 旨意同日下达并办结。
2. 人物身份立即改变。
3. 御案出现内廷复命。
4. 国策中枢把它标记为“内廷制衡外朝”路线证据。
5. 后续奏对只能追问后患、怨望、差遣风险，不能再把此事说成未下达。

---

## 迁移顺序

1. 文档定口径：本文件作为“下达/执行/回报”唯一解释。
2. UI 文案先改：禁止再出现“下达需 X 日”，统一为“预计复命 X 日”。
3. 增加 timing profile：把 `same_day`、`capital_short`、`administrative`、`field_operation`、`policy_program` 写入配置。
4. 增加即时旨意识别：净身、收押、革差、转民籍等先走 direct action。
5. 允许零日：`lead_days` 和 `exec_days` 对 same-day 类型允许为 0。
6. 御案复命类型收敛：正式结果全部落 `memorials(kind='复命')` 或细分复命 kind。
7. 奏对回访改名：把旧约追问从“回报”文案里剥离出来。
8. 增加测试，防止近身处置再次被通用长周期吞掉。

## 验收用例

### 同日净身

输入：

```text
下旨强行净身张三，没入内廷。
```

预期：

- 第 N 日即显示“已下达并办结”。
- `张三.status` 或身份字段当天变为太监/内廷。
- `lead_days=0`，`exec_days=0/1`。
- 御案当天或次日出现复命。
- 国策中枢出现“内廷制衡外朝”证据。

### 京中任免

输入：

```text
着李四署理户部郎中。
```

预期：

- 当天成命。
- 若无需部议，`delivery_days=0`。
- `work_days` 不应超过数日。
- UI 显示“承办中/已复命”，不显示“下达中”。

### 远省赈济

输入：

```text
拨银赈济陕西灾民，命巡抚十日内具奏。
```

预期：

- 当天成命。
- 传旨受陕西距离影响。
- 承办受财政、地方动乱、士绅阻力影响。
- UI 显示传旨日数、承办日数和预计复命日。

### 复命后追问

输入：

```text
朕看过复命，真实成效有没有水分？
```

预期：

- 进入召对，但上下文必须承认原旨已复命。
- 结果写入复盘/追问历史。
- 不重复生成同一正式复命。
- 若问出新任务，另起新旨意或履约承诺。

### 履约回访

输入：

```text
你上月答应联络某人支持新饷法，办到哪一步了？
```

预期：

- 归入奏对履约回访。
- 不显示为御案复命。
- 若形成证据，挂入国策中枢对应路线。
