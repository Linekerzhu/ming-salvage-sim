# 设计升级方案：半即时结算与策略深度改造

> 状态：设计稿 v1（2026-06）
> 对象：当前原型（月结算 + 月末 LLM 大结算管线）
> 目标：在不推翻现有 `decree → simulate → extract → apply` 管线的前提下，
> 把游戏从「月末交卷」改成「半即时推演」，同时补齐策略深度与信息黑箱。

---

## 0. 现状诊断（为什么月结算伤害了核心乐趣）

设计初衷是「把皇帝的意志压进庞大而迟滞的官僚体系」，但现在的实现是：

1. **反馈回路断裂**。玩家全月召对积旨 → 月末 `resolve_directives()`（decree.py）一次性结算。
   下旨与见效之间隔着一整个黑屏，官员的拖延、打折、阳奉阴违只在月末邸报里
   作为既成事实出现，玩家没有任何中途干预的机会。「迟滞的官僚体系」
   应该是玩家能感知、能博弈的过程，而不是月末读一篇作文。
2. **数值靠 LLM 软判定**。欠饷→哗变、民变触发都由推演官自由裁量
   （simulation.py），玩家无法形成稳定预期，策略规划无从谈起。
3. **官员与派系全被动**。官员只应答不主动奏报，派系只有 leverage/satisfaction
   两个被动评估字段，不会反扑、不会出招。皇帝永远是唯一行动者，
   「党争压力」名存实亡。
4. **黑箱没有实现**。`/api/characters` 直接暴露 loyalty/ability/integrity，
   npc_network 关系全透明。「识人」这个核心乐趣没有机制支撑。
5. **无中间态目标**。只有「撑到 1647」和失败两种结局，20 年 240 回合
   没有阶段性张力。

下面五个章节分别解决这五个问题。**第 1 章（半即时时间引擎）是地基，
其余章节都构建在它之上。**

---

## 1. 半即时时间引擎（核心改造）

### 1.1 设计原则

- **最小时间单位：日**。时间以可调速度自动流动（如 1 秒 = 1 天，可 1x/3x/暂停），
  也支持「跳到下一节点」。月不再是结算单位，只是日历刻度。
- **分层结算，控制 LLM 成本**：
  - **规则层（每日 tick，零 LLM）**：财政按日摊销、欠饷累积、issue bar 惯性漂移、
    指令执行进度推进、情报送达倒计时。纯 Python 数值运算。
  - **LLM 层（仅在节点触发）**：指令完成结算、事件爆发叙事、旬报/月报汇总、
    派系出招生成。LLM 调用从「月末一次巨型推演」变成「多次小型定向推演」，
    单次上下文更小、更聚焦，总成本可控甚至下降。
- **自动暂停（semi-real-time 的「semi」）**：以下情况时间自动停住，等玩家处置：
  - 红色急报（哗变、城破、重臣暴毙、弹劾风暴）
  - 一道旨意执行完毕 / 执行中途出现异常（见 §2）
  - 约定 due 日到期、密查结果送达
  - 玩家进入召对界面（御前奏对时天下静止，避免对话时数值跑飞）

### 1.2 数据结构

新增一张**调度表**，作为整个半即时系统的心脏：

```sql
CREATE TABLE scheduled_resolutions (
    id INTEGER PRIMARY KEY,
    kind TEXT,          -- directive_step | event_check | report | agreement_due
                        -- | intel_arrival | faction_move
    due_day INTEGER,    -- 绝对日序号（自 1627-10-01 起算）
    payload TEXT,       -- JSON：指令id / 事件id / 情报id 等
    status TEXT,        -- pending | fired | cancelled
    requires_llm INTEGER,
    auto_pause INTEGER  -- 触发时是否暂停时间
);
```

`game_state` 增加 `current_day`（绝对日）与 `time_speed`。
`turn` 字段保留，定义为 `current_day // 30 + 1`，所有现存月度逻辑可平滑映射。

### 1.3 主循环

```
每个 tick（一天）：
  1. apply_daily_flows()        # flows.py 现有月度公式 ÷30 按日摊
  2. advance_directives()       # 推进所有执行中指令的进度（§2）
  3. advance_issues_daily()     # issues.py 的 inertia ÷30
  4. pop_due_resolutions()      # 调度表里到期的节点
       ├─ requires_llm=0 → 纯规则结算（如欠饷阈值检查）
       └─ requires_llm=1 → 入 LLM 结算队列（异步，见 §1.4）
  5. check_hard_thresholds()    # §3 硬阈值扫描
  6. 若任何节点 auto_pause → 暂停时间，推送前端
```

### 1.4 LLM 异步结算队列

半即时下 LLM 延迟（数秒到数十秒）必须和游戏时间解耦：

- 节点触发 → 任务入队 → **游戏内时间该节点冻结**（该指令/事件标记为
  「结算中」，不再推进），其余世界继续流动。
- 结算完成 → 结果落库 → 以「奏报送达」的形式出现在御案上（天然的叙事包装：
  本来奏报从地方到京师就要时间，LLM 延迟被史实合理化了）。
- 并发上限 2~3 个结算任务，超出排队——这同时是成本闸门。
- 复用现有 `extract_scores_by_modules_with_agno()` 的四模块 schema，但每次
  只传该节点相关的局部上下文（一道指令 + 相关官员 + 相关地区），
  而不是整个天下盘面。**这是上下文瘦身的关键。**

### 1.5 「朔日大朝」保留月度仪式感

每月初一仍有一次汇总节点（auto_pause）：月度邸报（把当月各散点结算
浓缩成一篇，复用现有 simulator，但输入是已发生的结算记录而非待推演的盘面，
从「推演者」降级为「史官」，幻觉风险大降）、财政月账、官员考成摘要。
玩家保留「读月报做复盘」的节奏锚点，但月报不再是世界变化的唯一来源。

### 1.6 改造路径（对现有代码）

| 步骤 | 改动 | 涉及文件 |
|------|------|---------|
| 1 | game_state 加 current_day/time_speed；建 scheduled_resolutions 表 | db.py, models.py |
| 2 | flows.py 月度公式参数化为 per-day（÷30，保留月度入口做校验） | flows.py |
| 3 | tick 主循环 + WebSocket 时间推送（前端时钟/速度控件） | session.py, web_app.py, web/src |
| 4 | resolve_directives() 拆解：写诏书保留即时，推演+提取改为按指令分片入调度表 | decree.py, simulation.py |
| 5 | LLM 队列 worker（线程池 + 结果落库 + 推送） | 新建 ming_sim/scheduler.py |
| 6 | 朔日大朝月报（史官模式 simulator） | simulation.py, report.py |

> 建议先做 1~3 跑通「纯规则层的日 tick + 可暂停时钟」，此时游戏仍按月结算
> LLM，但时间已经流动；再做 4~5 把结算打散。两阶段都可独立验证。

## 2. 指令生命周期：让「迟滞的官僚体系」可见可博弈

> 2026 修订：本节里的 `lead_days` 只表示传旨/送达，不表示“下达”。玩家确认颁诏后应立即成命；完整口径见 [旨意周期与回报机制重排](./decree-cycle-and-reports.md)。

这是半即时引擎上最重要的玩法层。每道旨意不再是「月末一次性生效」，
而是一个有状态的过程：

```
颁诏成命(即时) → [传旨/送达 lead_days，可为0] → [承办 exec_days，可为0] → 御案复命
                                                    ↑
                                          中途异常节点（玩家可干预）
```

### 2.1 工期计算（规则层，玩家可见可预估）

```
exec_days = 基础工期(按指令类别查表)
          × 官署执行力修正(bureaucracy.organization_diagnostics 已有评分)
          × 距离修正(京师/北直隶 1.0，江南 1.3，西南边地 1.8)
          × 派系阻力修正(主办官员所属派系对该政策的立场，§4)
```

颁诏界面直接显示预估工期与风险等级——把现有 `directive_execution_assessments()`
的预评估从「给 LLM 看的提示」升级为「给玩家看的承诺」。
**策略性来源：玩家在「让能臣办（快但树敌）」与「让派系接受的人办（慢但稳）」
之间做真实取舍。**

### 2.2 中途异常：拖延、打折、阳奉阴违的暴露时机

每道执行中的指令每旬掷一次「执行检定」（规则层公式 + 主办官员隐藏属性 +
派系阻力），可能产出异常节点（入调度表，requires_llm=1，auto_pause=1）：

- **拖延**：进度停滞，主办官员上疏陈情（LLM 生成，给出真假难辨的理由）
- **打折**：执行规模缩水（截留三成），但奏报粉饰——玩家此刻看到的是
  粉饰版，真相需要密查（§5）
- **顶撞封驳**：六科给事中封驳、官员抗旨自辩，指令冻结等候圣裁
- **意外**：地方实情与庙算不符（赈灾粮到了但灾民已变流寇）

**玩家中途干预选项**（每项本身也是一道小指令，有自己的小工期）：
催办（加速但 unrest/官员怨气+）、换人主办、加拨钱粮、收回成命（威望-）、
派员督办（占用一名官员）。

> 这一章直接兑现设计初衷里「官员可以推诿、试探、敷衍、暗中反抗」——
> 但发生在执行过程中、玩家眼前，而不是月末作文里。

### 2.3 数据结构

`directives` 表增加：`status(draft/issued/in_transit/executing/stalled/done/aborted)`、
`progress(0-100)`、`exec_days`、`assignee_id`、`integrity_actual`（真实执行率，
隐藏）、`integrity_reported`（奏报执行率，玩家可见）。
两个执行率的差值就是「欺上」的量化，密查机制（§5）的查证对象。

## 3. 硬阈值 + LLM 叙事分离（数值可信度）

原则：**「是否发生」由规则决定，「如何发生」由 LLM 叙述。**

把现在散落在 LLM 自由裁量里的关键因果固化为日 tick 扫描的硬规则表
（content/ 下新建 `threshold_rules.json`，数据驱动可调）：

| 触发条件（规则层扫描） | 必然后果 | LLM 职责 |
|---|---|---|
| army.arrears > 3 个月饷 且 morale < 40 | 哗变事件立项 | 写哗变的过程、领头者、诉求 |
| region.unrest > 70 且 grain_security < 1 个月 | 民变立项 | 写起事的火星与首领 |
| issue.bar 触底（fail_condition） | effect_on_fail 必然落库 | 写失败的叙事 |
| 国库 < 0 连续 3 个月 | 强制「捐俸/加派/搜刮」三选一危机抉择 | 写朝议各方反应 |
| 官员 grievance（新增怨气值）> 80 | 该官员进入消极怠工/请辞/倒向反对派 | 写其表现 |

配套：前端给每条硬规则做**预警仪表**（如「宣大军欠饷 2.4/3.0 个月」），
玩家能看到悬崖在哪里——策略规划由此成为可能。这不破坏黑箱：
黑箱针对的是「人心」，而钱粮兵额这类账面数字，皇帝本来就该看得到
（最多让账面数字本身被瞒报，那是 §5 的菜）。

## 4. 派系主动 AI 与官员主动奏报（让世界出招）

### 4.1 派系出招（每旬一次，调度表 faction_move 节点）

派系增加字段：`agenda`（本阶段诉求，如东林「翻案逆案、清查阉党」）、
`heat`（敌意度，玩家政策每次损其利益则累积）。每旬规则层按 heat 概率
决定是否出招，LLM 生成具体招式内容：

- **弹章**：弹劾政敌或皇帝亲信（奏疏流送达御前，玩家批红表态——
  留中、申斥、查办，每种表态都改变两派 heat 与官员怨气）
- **联名请愿 / 廷议发难**：就某 issue 集体施压，附带「不从则集体怠工」的暗示
- **市恩 / 荐人**：往要害官署塞自己人（人事提案送达，玩家批红）
- **暗手**：散播流言（污染玩家的情报置信度，§5）、地方掣肘（给某指令
  叠加派系阻力修正）

### 4.2 官员主动奏报（奏疏流）

半即时下，奏疏不再是被动菜单，而是**随时间陆续送达御案的流**：
请款、荐人、告变、请罪、密揭。每份奏疏带 `urgency` 与「留中天数」计数器——
**积压本身有后果**（上疏人怨气+、派系解读为风向）。批红动作轻量化：
照准 / 驳 / 留中 / 召对面议（转入召对）/ 发部议（转给相关官署，出廷议结果）。

> 这一章把「批阅奏疏」从设计文档里的概念变成核心日常操作，
> 也让玩家从「唯一行动者」变成「在各方出招的牌桌上坐庄」。

### 4.3 成本控制

派系出招与奏疏生成用主 model（非 advanced），单次生成 ≤500 token，
每旬全局上限 N 份（如 3~5 份），按 heat 与剧情权重竞争配额。

## 5. 信息黑箱与密查体系（兑现「识人」乐趣）

### 5.1 属性遮蔽：印象值替代真值

API 层停止暴露官员真值。玩家看到的是**印象档案**：

```
对外印象 = 真值 + 观测噪声（噪声随交互次数收敛）
展示形式 = 模糊评语 + 置信度（"似可信重（颇有把握）" / "忠悃难测（仅凭风闻）"）
```

新增 `perception` 表：`(character_id, attr, perceived_value, confidence, last_basis)`。
更新来源：召对表现（dialogue_audit 已产出 speech_acts，正好作为修正信号）、
指令执行结果复盘（integrity_reported vs integrity_actual 被揭穿时大幅修正）、
密查报告、他人评价（注意：他人评价本身带立场偏差——东林评阉党必贬）。

### 5.2 密查指令（厂卫/科道两条线）

作为一类特殊指令走 §2 的生命周期（有工期、会失败、会被反侦）：

- **东厂/锦衣卫线**：快、准，但每次动用累积「厂卫横行」issue bar
  （言官弹劾、民间怨望），且厂督本人是否可信又是一层黑箱——查人的人也要被查。
- **科道/巡按线**：慢、带派系滤镜（巡按是谁的人，报告就偏向谁），但无政治成本。

产出**情报报告**：指向某官员真实属性区间、某指令真实执行率、某派系暗中动作。
报告带 `credibility`，且可能是错的（被反侦时对方喂假情报）。

### 5.3 承诺—兑现闭环升格

现有 negotiation_agreements 已有 due_turn 与违约 blocker，升格为双向可见：

- 玩家失诺 → 该官员 perception 体系反向运作：**官员对皇帝也有信任值**，
  失信则后续握手 threshold 抬高、执行打折概率升——「君无戏言」成为硬约束。
- 官员失诺 → 自动生成「可问罪抓手」，玩家可在召对中出示（修正握手评分）
  或交科道发起弹劾（指令化）。

## 6. 阶段目标与中兴指数（节奏与成就感）

- **中兴指数**（0-100，月度计算）：财政健康、九边稳定、流寇压制、吏治、
  民心五个分项加权。不是胜利条件，而是**趋势仪表**——朔日大朝展示折线。
- **阶段诏题**：每个历史阶段（1628-29 站稳脚跟 / 1629-31 己巳之变考验 /
  1631-36 流寇与辽东双线 / …）给 2~3 个可量化的阶段目标
  （如「己巳之变前，蓟镇 supply ≥ 60」），完成给威望与叙事奖励。
  既是软教程（替代未实现的 #4 开局教程），又把 240 个月切成有张力的章节。
- **多结局光谱**：撑到 1647 时按中兴指数 + 关键 issue 状态结算结局
  （回天乏术 / 划江而治 / 中兴在望 / 乾纲独断的代价…），替代现在的二值结局。

## 7. 实施路线图

| 阶段 | 内容 | 价值 | 依赖 |
|------|------|------|------|
| **P1 时间地基** | §1.6 步骤1-3：日 tick、调度表、可暂停时钟、财政按日摊 | 时间流动起来，月结算暂时保留 | 无 |
| **P2 指令生命周期** | §2 全部 + §1.6 步骤4-5：结算打散、异步 LLM 队列 | 半即时核心体验成立 | P1 |
| **P3 硬阈值** | §3：threshold_rules.json + 预警仪表 | 数值可信、可规划 | P1（可与 P2 并行） |
| **P4 世界出招** | §4：派系 AI + 奏疏流 + 批红 | 对抗性、日常操作密度 | P2 |
| **P5 黑箱** | §5：印象值 + 密查 + 双向信任 | 兑现「识人」核心乐趣 | P2（perception 可先行） |
| **P6 节奏层** | §6：中兴指数 + 阶段诏题 + 多结局 | 长线动力 | P3 |

P1+P3 合计改动较小且不动 LLM 管线，建议作为第一个落地里程碑。

## 8. 风险与对策

- **LLM 成本上升？** 结算次数变多但单次上下文大幅瘦身（局部盘面替代全局盘面），
  且规则层接管了大量原本靠 LLM 判定的因果。预计持平或下降；token_stats.py
  已有按角色统计，P2 上线后对比验证。
- **节奏失控（玩家被节点轰炸）？** auto_pause 分级：红色必停，黄色仅推送角标；
  每旬节点配额上限；提供「跳到下一红色节点」按钮。
- **存档兼容**：current_day 从 turn 反推（turn×30），旧档指令一律视为已完成。
- **LLM 推演与规则层打架**：提取 schema 中凡有硬规则覆盖的字段（哗变、民变、
  结案）改为只读——LLM 不再有权写这些 delta，只能叙述。
